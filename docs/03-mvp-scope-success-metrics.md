# MVP Scope & Success Metrics

---

## 1. 本期 MVP 要验证的核心假设

| 假设编号 | 假设内容 | 验证方式 |
|---|---|---|
| H1 | 飞书内就能承载领导督办闭环，不需要跳到其他系统 | 全流程（创建→更新→提醒→月结）在飞书内完成 |
| H2 | 只要 Leader 和员工的更新动作足够轻，周跟进和月结就可以制度化 | 观察周完成率和延期率的趋势 |
| H3 | 老板真正需要的不是更多页面，而是一个可信的风险视角 | 老板驾驶舱提供 Leader 维度的延期/风险汇总，验证是否满足决策需求 |

**MVP 不是要做一个完美的任务管理系统。MVP 是要验证：用一个轻量工具能不能让督办循环转起来。**

---

## 2. MVP 必做能力

| 能力 | 对应旅程 | 面向角色 | 验证的假设 |
|---|---|---|---|
| 创建任务 | 旅程 1 | Leader、老板 | H1 |
| 指派任务 | 旅程 1 | Leader、老板 | H1 |
| 更新进展 | 旅程 2 | 员工 | H2 |
| **双入口：多维表格（录入/协作） + 网页应用（管理/看板）** | 旅程 1、2 | Leader、员工 | H1、H2 |
| 周提醒 | 旅程 4 | 全角色 | H2 |
| 延期提醒 | 旅程 2、4 | 员工、Leader | H2 |
| 月结与继承 | 旅程 5 | 全角色 | H1 |
| 老板查看 Leader 风险项 | 旅程 3 | 老板 | H3 |

### 双入口说明

MVP 采用"双入口"模式：
- **多维表格**：Leader 和员工日常录入、编辑任务的主要入口（他们已有使用习惯）
- **网页应用**：管理视图、老板驾驶舱、统计看板、任务详情
- **同步方向**：多维表格的编辑 → 回写中心主档 → 同步到网页应用展示。网页应用的操作 → 写入中心主档 → 同步到多维表格。
- **这意味着基本的多维表格双向同步是 MVP 能力**，不是延后能力。

## 3. 可延后能力

| 能力 | 延后原因 | 对应里程碑 |
|---|---|---|
| 飞书任务同步 | 先跑通多维表格 + 网页应用双入口 | M3+ |
| 飞书日历同步 | 同上 | M5+ |
| 飞书卡片内直接操作 | 先用提醒卡片跳转，再做卡片内编辑 | M3+ |
| 冲突处理后台（人工裁决 UI） | MVP 先走简单冲突策略（last write wins），复杂人工裁决台后做 | M5+ |
| Leader 团队统计看板（增强版） | MVP 先做基本的 Leader 任务列表，增强统计后做 | M4 |
| 复杂权限（字段级） | MVP 用简单角色控制即可 | M4+ |
| 协作者管理 | MVP 以单一负责人模型为主 | 待定 |

---

## 4. 明确不做

以下能力**在整个产品生命周期内都不做**，不是"延后"：

- 不做通用项目管理能力（不替代 Jira / Linear / Asana）
- 不做 OKR 体系
- 不做复杂审批流
- 不做组织外开放（仅限飞书组织内部）
- 不做过多个性化配置（统一规则）
- 不做"所有飞书触点都实时同步"的完美形态
- 不做独立移动 App（依托飞书生态）

## 5. 功能验收标准

MVP 发布前，以下每一条都必须通过验证：

| 编号 | 验收条件 | 验证方法 |
|---|---|---|
| F1 | 老板能创建并指派重点任务给 Leader | 端到端操作验证 |
| F2 | Leader 能在多维表格中创建、编辑任务 | 端到端操作验证 |
| F3 | Leader 能拆解任务并转派给团队成员 | 端到端操作验证 |
| F4 | 员工能在飞书内 3 步以内更新进度（多维表格或网页应用） | 操作步骤计数 |
| F5 | 多维表格编辑后，网页应用能看到更新；反之亦然 | 双向同步验证 |
| F6 | 系统每周一 09:00 自动推送周提醒到飞书 | 定时任务验证 |
| F7 | 到期未完成的任务自动触发延期提醒 | 模拟延期场景 |
| F8 | 月初系统自动完成月结、生成月报、继承未完成任务 | 月结 dry-run + 实际执行 |
| F9 | 老板能按 Leader 维度查看任务分布和风险项（延期 + 多次继承） | 驾驶舱页面验证 |

## 6. 业务成功标准

### 风险的定义（已确认）

一个任务被标记为"风险项"，当且仅当满足以下任一条件：
- **延期**：当前时间 > 截止时间，且任务未完成
- **多次继承**：`carry_over_count >= 2`（已经被继承 2 次或以上，说明长期未完成）

### 核心指标

上线后用以下指标持续跟踪：

#### 指标 1：周完成率

- **定义**：本周完成的任务数 / 本周应完成的任务数
- **口径**：
  - 分子 = 本周内 `completed_at` 有值（状态变为 done）的任务数
  - 分母 = 截止时间（`due_at`）落在本周内，且状态不为 `cancelled` 的任务数
  - 统计周期：周一 00:00 ~ 周日 23:59
- **目标**：首月建立基线，持续观察趋势
- **采集方式**：系统自动统计

#### 指标 2：周延期率

- **定义**：本周新增延期的任务数 / 本周活跃任务数
- **口径**：
  - 分子 = 本周内首次变为 `is_overdue = true` 的任务数
  - 分母 = 状态为 `assigned` / `in_progress` / `blocked` / `pending_review` 且 `month_bucket = 当月` 的任务数
  - 统计周期：周一 00:00 ~ 周日 23:59
- **目标**：趋势应逐周下降
- **采集方式**：系统自动统计

#### 指标 3：周新增任务数

- **定义**：本周新创建的任务数
- **口径**：
  - `created_at` 落在本周内的任务数（不含系统继承生成的）
  - 统计周期：周一 00:00 ~ 周日 23:59
- **目标**：反映系统活跃度。如果持续为 0，说明没人在用
- **采集方式**：系统自动统计

#### 指标 4：月结完成时效

- **定义**：月结任务是否在每月 1 日自动完成
- **口径**：
  - 成功 = 月结主流程在每月 1 日 10:00 前完成，月报在 10:30 前推送
  - 失败 = 未在规定时间内完成，或需要人工干预
- **目标**：100% 自动完成
- **采集方式**：月结日志记录

## 7. 上线后首月如何判断成败

### 判断时间点
上线后第 30 天（第一次月结完成后）。

### 成功判据

| 条件 | 判断标准 |
|---|---|
| **流程跑通** | 第一次月结成功完成，月报自动推送 |
| **Leader 在用** | ≥ 3 个 Leader 主动在系统中创建任务（多维表格或网页应用），而不是继续用旧表格 |
| **双入口在用** | 多维表格和网页应用都有操作记录，数据能双向同步 |
| **老板在看** | 老板至少使用过一次驾驶舱查看 Leader 维度数据 |
| **风险可见** | 延期任务和多次继承任务在驾驶舱中正确标记并展示 |

### 失败信号

| 信号 | 含义 |
|---|---|
| Leader 不录入任务 | 产品对 Leader 的价值不够——需要回到旅程 1 重新设计 |
| 周新增任务数持续为 0 | 没人在用——产品推行策略有问题 |
| 周延期率无变化或上升 | 提醒和督办机制未生效——需要检查提醒是否触达 |
| 月结需要人工干预 | 系统稳定性不够——需要修复技术问题 |
| 老板从未使用驾驶舱 | 要么老板不需要这个，要么展示不够直观——需要回到旅程 3 重新设计 |

## 8. 指标数据来源映射

| 指标 | 数据来自 | 统计频率 |
|---|---|---|
| 周完成率 | `task` 表（`completed_at` + `due_at`） | 每周 |
| 周延期率 | `task` 表（`is_overdue` 变化） | 每周 |
| 周新增任务数 | `task` 表（`created_at`，排除 `carry_over`） | 每周 |
| 月结完成时效 | 月结日志 | 月度 |
