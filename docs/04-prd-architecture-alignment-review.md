## 四、应回到产品层重新定义的内容

以下内容做了实现决策，但对应的产品决策尚未冻结：

### 4.1 继承策略："新建记录"是否是最优方案？

**当前状态**：`business-rules.md` 第 11 节和 `monthly-close-rules.md` 第 6 节已决定"继承时新建记录，不修改原记录"。`db-schema.md` 据此设计了 `carried_from_task_uid` 和 `carry_over_count` 字段。

**问题**：这是一个影响用户体验的产品决策，不仅仅是技术决策。新建记录意味着一个拖了 3 个月的任务在系统中有 3 条记录。Leader 在查看时会看到什么？老板在统计时算几次？这些产品层面的问题没有先回答就直接写了数据模型。

**建议**：在 Product Brief 的 Q 列表中标注为待确认项。可能需要引入"任务链"概念或在 UI 层做聚合展示。

### 4.2 协作者功能：MVP 是否需要？

**当前状态**：`field-dictionary.md` 定义了 `collaborators` 字段，`business-rules.md` 有协作者规则，`prd.md` 提到"支持设置协作者"。

**问题**：核心旅程中没有"协作者"角色。5 条旅程的主角是 Leader、员工、老板。协作者能力增加了权限复杂度和 UI 复杂度，但不出现在任何成功 Moment 中。

**建议**：从 MVP 中移除。`collaborators` 字段可保留在 schema 但不暴露在 UI 和 API 中。

### 4.3 "老板关注"标记的操作路径

**当前状态**：`business-rules.md` 和 `permission-matrix.md` 定义了 `boss_attention_flag`，只有老板和 PMO 能标记。

**问题**：旅程 3 中老板确实需要标记重点任务，但当前文档没有定义：老板在什么场景下标记？标记后触发什么（提醒？加权？展示高亮？）？取消标记的场景？这是产品行为定义，不是字段定义。

**建议**：在 User Journey Map 旅程 3 中补充老板关注的完整交互流程。

### 4.4 API 响应字段命名（snake_case vs camelCase）

**当前状态**：`api-contracts.md` 和 DTO 定义使用 snake_case，Drizzle ORM 返回 camelCase，前端两者都兼容。

**问题**：这看起来是技术问题，但实际上影响前后端协作效率和 API 文档质量。应该作为架构约定冻结，不需要回到产品层，但需要在架构层明确。

**建议**：这是架构层决策，但需要在代码实现前冻结。建议统一为 snake_case（与文档一致）并在 API 层做转换。

### 4.5 "风险项"的产品定义 — ✅ 已决策

**决策**：一个任务被视为"风险项"当且仅当满足以下任一条件：
- **延期**：当前时间 > 截止时间，且任务未完成
- **多次继承**：`carry_over_count >= 2`（已被继承 2 次或以上，说明长期未完成）

**影响**：老板驾驶舱的风险视图可据此实现。旅程 3 中"5 分钟内找到风险点"有了明确的数据口径。

## 五、对第一用户（Leader）支持的审查

**当前问题**：现有文档把 Leader 当作"分发器"——接收老板任务、转派给员工、验收完成。但根据产品定义，Leader 是 **MVP 第一用户**，最核心的场景是 **Leader 主动写入自己的月度计划**。

以下缺失需要补充：

| 缺失 | 影响 | 建议 |
|---|---|---|
| 没有 Leader "月初计划"的产品设计 | Leader 的第一个动作没有被设计 | 在旅程 1 基础上设计"月初规划"页面 |
| Leader 视图在 MVP 中优先级不够 | `milestone-plan.md` 把 Leader 视图放在 M4 | 应将 Leader 的基本任务看板提前到 MVP |
| Leader 的价值感缺失 | 当前设计中 Leader 只是"给老板填数据的人" | 需要让 Leader 觉得"这个工具帮我管理团队"，而不是"给老板汇报" |

## 六、对"持续更新进度"这一关键断点的审查

产品定义明确指出：**执行人持续更新进度是最容易断的环节**。审查现有文档对此的支撑：

### 已有支撑
- `notification-rules.md` 定义了周一提醒和临期提醒 ✅
- `state-machine.md` 有 in_progress → blocked 路径 ✅
- 更新接口已实现（PATCH /tasks/:uid） ✅

### 缺失支撑

| 缺失 | 影响 | 建议 |
|---|---|---|
| 没有"卡片内直接更新进度"的 MVP 方案 | 员工必须跳到网页应用才能更新，步骤 > 3 | 待确认：MVP 是否包含飞书卡片交互？如果不包含，至少要保证网页更新流程极简 |
| 没有"提醒未响应"的升级机制 | 提醒发了但员工不理，没有后续动作 | 待确认：是否需要"连续 N 天未更新 → 通知 Leader" |
| 没有正向反馈设计 | 员工更新进度后没有回应，觉得更新无意义 | 建议：Leader 能看到实时更新 + 月报中展示"更新最积极的人" |
| 进度更新的"最少必填"未定义 | 如果必须填进度百分比 + 文字描述，太重 | 建议：最轻量模式只需改进度百分比（一个滑块） |
