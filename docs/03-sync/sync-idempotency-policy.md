# 幂等与对账策略

## 1. 目标

保证双向同步在重复事件、网络抖动、重试场景下仍然只生效一次，并具备自动修复能力。

## 2. 幂等设计

### 幂等键
`source_type + source_event_id`

### 两层保留策略

- **热幂等缓存（Redis）**：保留 7 天，用于实时去重和快速判定
- **持久幂等审计日志（PostgreSQL）**：保留 90 天，用于审计、回放和对账

### 最低要求
- 每次外部事件都要带来源和事件 ID
- 无事件 ID 的内部任务，要生成内部幂等键
- 热缓存过期后仍可通过持久日志判定是否已处理

## 3. 版本控制

每条任务保留：

- `version`：业务版本
- `sync_version`：同步版本

原则：
- 写入前校验版本
- 写入成功后递增版本
- 过期版本不得覆盖新版本

## 4. 防循环写回

每次由系统触发的外部写操作，都应生成：

- `causation_id`
- `sync_hash`

当外部系统把同一变更再推回来时，可根据 hash / causation_id 判定为回声事件并忽略。

## 5. 对账机制

### 5.1 实时对账
写操作成功后比对核心字段是否一致。

### 5.2 定时对账
- 飞书任务：每 15 分钟
- 飞书日历：每 30 分钟
- 多维表格：每小时
- 全量修复：每日凌晨

### 5.3 对账字段
- status
- progress_percent
- latest_progress
- due_at
- completed_at
- assignee（只校验，不从任务侧覆盖）

## 6. 异常分级

- P1：老板关注任务不同步
- P2：普通任务执行字段不同步
- P3：展示型字段不同步

## 7. 修复策略

- 自动重试
- 自动补写
- 标记冲突
- 人工处理
